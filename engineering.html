01 · 开发协作、规范与架构边界

从个人代码质量到团队可维护性；关联 TypeScript、模块重构项目。

L1–L5
要解决的问题：多人迭代时防止接口变更失控、重复代码、隐性依赖与未经审查的高风险提交。
L1｜接手一个多人维护的前端仓库，第一周先了解什么？
参考：先摸清业务关键路径、依赖图、运行环境、包管理锁文件、构建/测试脚本、发布频次、故障记录和代码所有权；确认能否从干净环境复现构建。先画依赖和风险地图，不急着全面重构。
L2｜ESLint、Prettier、TypeScript 分别防什么？
参考：Prettier 统一排版；ESLint 检查可配置的代码模式、部分潜在错误和团队约定；TypeScript 在编译期检查类型关系，但不验证线上 JSON 的真实结构。三者不能替代单测或运行时输入校验；严格程度需根据遗留代码逐步调整。
L3｜如何划分模块与组件边界，避免循环依赖？
参考：按业务能力或稳定职责划分，公共层依赖方向明确；组件公开 props/events 契约，跨模块通过明确接口而非随意 import 内部实现。用依赖分析和约束规则辅助发现循环，避免“全部放 utils”的伪复用。
L4｜Code Review 与分支保护怎么真正形成质量门禁？
参考：小 PR、可复现说明、风险分级、指定代码所有者、必需状态检查和禁止未经授权直接合并；审查关注行为、兼容、测试和安全而非只挑格式。CODEOWNERS 本身是所有者匹配机制，是否强制审批还依赖仓库规则和权限设置。
L5｜遗留项目无法一次启用严格规则，怎样渐进式治理？
参考：先固定基线、限定新改动不增加告警，为高风险目录设置更严格门禁；逐步修复存量并记录豁免原因/期限。衡量新增缺陷、PR 反馈周期和回归成本，避免为了“零告警”让项目无法发布。
取舍：Monorepo 适用于共享包与跨项目协作，但会增加依赖图、构建缓存和权限治理成本；微前端同理，先看独立部署边界。
最小实践及验收：在公开 demo 增加 lint / typecheck / test 脚本、CODEOWNERS 示例与 PR 模板；故意提交类型错误和未授权修改，验证是否被检查阻止。仓库保护规则需有权限并经所有者确认才启用。
官方资料：TS Handbook · CODEOWNERS

02 · 构建体系与产物治理

Webpack/Vite、模块图、Tree Shaking、拆包与缓存；关联 构建基础、升级项目。

L1–L5
要解决的问题：构建慢、首屏依赖过重、版本间资源失配以及产物不可追溯。
L1｜一条构建链从源码到可部署资源经历哪些步骤？
参考：模块解析 → 文件转换 → 依赖图与代码分割 → 优化/压缩 → 输出 HTML、JS、CSS、资源及 manifest（视工具配置）。区分开发服务器的按需处理和生产构建的打包行为；先说明当前项目实际使用哪个版本。
L2｜Webpack 的 loader 和 plugin 有什么边界？Vite 开发为什么往往快？
参考：loader 重点处理模块内容转换，plugin 介入编译生命周期和输出等更广工作；Vite 开发通常借助浏览器原生 ESM、依赖预构建和按需转换，避免启动时处理整张应用模块图。不要把开发启动快推导为所有生产构建都更快。
L3｜如何设计 splitChunks / 动态 import，不造成碎片化？
参考：依据首屏关键路径、复用频率、依赖体积、缓存稳定性和请求开销划分；路由级代码分割常是入口。验证 waterfall、执行时间和真实用户 LCP；避免把高频首屏依赖拆到更多串行请求里。
L4｜Tree Shaking 失效时如何排查？
参考：确认 ESM 导入导出、sideEffects 声明与模块顶层副作用，检查转译是否破坏静态结构，再观察构建统计与压缩结果。不能简单设置 sideEffects:false 而丢掉必要的 CSS 或初始化副作用。
L5｜生产环境资源 hash、HTML 缓存和发布如何配合？
参考：内容指纹静态资源通常可长缓存，HTML/入口应有可控更新策略；保留旧版本静态产物支持长时间打开的旧页面，提供 chunk 加载异常恢复。用构建 SHA、manifest 和 source map 对应 release；source map 的公开策略应符合安全与调试要求。
取舍：更多 chunk 并不等于更快；CDN、preload、缓存只解决各自瓶颈。首屏体验与构建速度分别验证。
最小实践及验收：做一个有三路由和大型依赖的 demo：记录构建体积与首屏请求，增加动态 import 并对比；模拟旧 HTML 加载新部署时的 chunk 请求，写出恢复策略。
官方资料：Webpack Code Splitting · Why Vite · web.dev 代码分割

03 · 自动化测试、质量门禁与 AI Code Review

从类型检查到关键用户旅程；关联 AI Agent 项目。

L1–L5
要解决的问题：代码“编译通过”却造成回归；AI 生成代码看似合理但隐藏边界缺陷。
L1｜lint、类型检查、单测、集成、E2E 各自覆盖什么？
参考：lint/TS 抓静态问题；单测验证小单元；集成测模块与边界协作；E2E 走真实浏览器关键路径。没有哪一层可替代所有其他层，按变更风险选择组合。
L2｜哪些逻辑值得优先单测？如何避免脆弱测试？
参考：优先可确定、风险高的纯函数和状态机：分桶、权限展示、请求去重、时间处理；优先验证外部行为与边界输入，不过度断言内部实现细节。Mock 第三方接口时保留至少一层契约/集成测试。
L3｜接口变化或第三方 SDK 升级，怎样防兼容性事故？
参考：明确请求/响应契约与版本兼容；运行时校验不可信数据，维护错误态与降级场景；通过测试环境集成、契约测试或灰度验证。TypeScript 声明在运行时被擦除，不会自动验证后端返回值。
L4｜AI Coding 生成一个功能，如何制定验收而不是只看能运行？
参考：需求转成可测的输入、输出、交互、异常与权限约束；AI 生成后人工审查依赖、边界、测试以及是否无关修改，再执行 lint/typecheck/test/E2E。对不稳定的模型输出要在确定性代码层建立 schema 和业务规则校验。
L5｜如何设计合理的 CI 门禁，测试 flaky 怎么办？
参考：PR 至少跑可复现的静态检查、关键单测和构建；高风险改动增加集成/E2E。flaky 测试先收集失败原因并隔离修复，重跑只做诊断不能长期把失败冲掉；门禁时长与反馈速度需平衡。
取舍：并非所有 UI 都需要大量快照；测试覆盖率是线索不是质量结论。AI 辅助 Review 不能取代代码所有者与实际执行的检查。
最小实践及验收：为请求竞态状态机编写 4 个用例：正常返回、超时、旧响应迟到、取消后重试；故意引入旧响应覆盖 bug，确认至少一个测试失败，再修复变绿。
官方资料：Playwright · Vitest · TS

04 · CI/CD、环境隔离与可追溯发布

提交 → 检查 → 构建 → 制品 → 审批 → 部署；关联 构建迁移项目。

L1–L5
要解决的问题：靠人工构建无法复现，测试环境与线上产物不一致，出了事故找不到对应版本。
L1｜从 PR 到生产发布，你会画出哪些关口？
参考：PR 静态检查和测试 → 主分支构建不可变制品 → 预发部署与关键路径验证 → 人工或规则审批 → 生产发布 → 发布后监测。发布和自动部署不是同义词；按业务约束定义审批权。
L2｜依赖安装与构建如何保证可复现？
参考：固定 Node 与包管理器版本、提交 lockfile、使用 frozen/immutable install、记录构建环境和 commit SHA；缓存必须可失效，不能把依赖缓存命中当成依赖正确。产物由同一构建生成而非各环境各编一次。
L3｜dev/test/staging/prod 的配置及密钥怎么管理？
参考：区分可公开的前端配置与服务端密钥；所有打进浏览器 bundle 的变量都应视为公开。部署密钥用受控 secret 管理、最小权限和短期凭证，绝不把 token 写入前端源码、日志或 PR 构建。外部贡献者 PR 不应获取生产凭证。
L4｜如何防止并发发布互相覆盖，回滚到什么东西？
参考：基于环境设置部署串行/并发组与审批策略；保留不可变构建制品、配置版本和发布清单。回滚需要同时考虑静态资源、HTML、功能配置、API 与数据库兼容性，不能只执行 git revert 就声称恢复。
L5｜发布失败如何发现、停止并追溯？
参考：把 commit、artifact、release 和监控告警关联；设置关键检查点、发布窗口及负责人与手动停止路径。灰度指标异常时暂停扩量，记录操作与影响范围，验证旧版本业务路径恢复。
取舍：自动化程度由项目和授权范围决定；生产环境不应默认给 CI 永久写权限。GitHub Actions 的 permissions 可收紧 GITHUB_TOKEN，concurrency 能限制同组并发，但不能代替应用层回滚。
最小实践及验收：在独立 demo 配置 PR 运行质量门禁；制造一次类型错误让工作流失败，修复后成功。正式部署前另行设计密钥、审批和制品归档，不能把下面的示例误称已发布生产。
官方资料：Actions workflow syntax · OWASP CI/CD 安全

05 · 灰度、Feature Flag 与回滚演练

线上风险控制；关联 灰度项目、场景题。

L1–L5
要解决的问题：新版本风险集中爆发、发布开关失灵、旧资源失效和无法及时止损。
L1｜全量、按比例灰度、按用户分组与 A/B Test 有何区别？
参考：灰度侧重降低发布风险，A/B Test 侧重比较定义明确的实验方案；按用户 ID 的稳定 hash 分桶可维持归属，比例值只决定覆盖范围。实验的分母、曝光时点和随机化单位必须明确。
L2｜前端如何处理远程配置、离线和缓存？
参考：配置包含版本、时间、有效期和默认策略；下发失败时使用可用缓存或安全默认变体；高风险权限规则必须服务端强制执行。配置改变时评估正在进行的订单/会话是否可中途切换。
L3｜一键关闭功能开关是否就相当于回滚？
参考：不是。Flag 只关闭受控路径；不可逆 API 写入、schema 变更、旧客户端和已经执行的支付/消息副作用还需补偿或兼容方案。紧急止损也要有触发条件和执行权限。
L4｜前端 JS 静态资源缓存导致版本错配，怎么恢复？
参考：保留旧 content-hash 资源、合理缓存 HTML、确保 API 兼容窗口；异步 chunk 失败可提示刷新或限定重试。service worker 参与时需考虑其更新生命周期，不能简单清空所有用户缓存。
L5｜如何组织一次真实的回滚演练并定义通过？
参考：记录故障注入前条件、发现机制、决策人、关闭开关/回滚步骤、恢复验证与耗时；确认关键业务流程与监控恢复，而不仅是页面能打开。演练必须在授权测试环境，避免制造真实用户影响。
取舍：不要为了“有灰度”引入无法运维的规则引擎；简单配置与受控发布足够时应避免过度设计。
最小实践及验收：在本地实现稳定分桶、配置断网兜底和一键关闭；模拟旧入口引用旧 chunk，完成一次可重复的切回演练并写复盘。

06 · 监控告警、稳定性与反馈闭环

从观测到故障恢复，再反哺前五个阶段；关联 监控项目、性能基础。

L1–L5
要解决的问题：线上问题只能靠用户投诉、缺少定位上下文、性能优化无法评价效果。
L1｜为什么要同时监控性能、错误、接口与业务？
参考：浏览器 Web Vitals 描述部分体验，JS/资源错误描述运行失败，接口指标描述服务依赖，业务指标反映关键流程；任何单一信号都可能漏报。先定义对应用户场景、统计口径、分位数及责任方。
L2｜怎么采集 LCP/INP 与业务首屏？
参考：优先使用成熟 web-vitals 采集并注意页面生命周期与有效样本；业务首屏需约定关键数据与组件渲染完成边界，nextTick 只保证 Vue DOM 更新时机，不单独证明浏览器已经绘制。网络较差设备应单独分群。
L3｜如何让采集 SDK 足够轻且遵守隐私要求？
参考：采样、批量和频率控制，严格字段白名单、PII 脱敏与上报失败兜底；避免发送令牌、表单和请求体。监控自己也监控上报失败率与主线程开销，不能因监控导致新卡顿。
L4｜告警爆炸时，如何确定影响范围并处理？
参考：按 release、路由、设备、地区/网络类型和错误 fingerprint 去重聚合，关联变更记录，先判断是否需要关闭开关或回滚。阈值结合基线、样本量和持续时间，不能把每个 JS 错误都当同级事故。
L5｜一场事故复盘如何反哺工程化？
参考：建立时间线、用户影响、触发条件、根因、止损过程与证据；将修复落到自动化测试、发布检查、告警规则或文档负责人。追踪复发率、发现/恢复耗时；复盘强调系统改进，不靠猜测动机。
取舍：指标改善须按相同口径和人群比较；高采样率提升细节但有成本与隐私约束。不要用 Lighthouse 分数替代线上用户体验。
最小实践及验收：测试环境发布两个版本，一个引入明确可控的错误；用 release 标签关联错误，验证报警→止损→恢复→新增回归测试的闭环。

练习工作流示例（不是本仓库已启用的 CI）

以下仅用于一个确实提供 lint、typecheck、test、build npm scripts 且提交了 package-lock.json 的 Node 项目。将其保存为 .github/workflows/ci.yml 前需调整 Node 版本、权限和测试命令；当前静态 HTML 题库不需要照搬。

name: Demo CI
on:
  pull_request:
permissions:
  contents: read
jobs:
  checks:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '22'
          cache: npm
      - run: npm ci
      - run: npm run lint
      - run: npm run typecheck
      - run: npm test -- --run
      - run: npm run build

这是教学用最小示意，不包含生产部署步骤；实际 action 版本、供应链策略与锁文件管理应按项目安全策略核对。参见 GitHub 官方工作流语法。

工程化面试总答题框架

  1. 先说明系统规模、部署方式、现有流程与真实痛点。
  2. 画出变更路径：谁提交、谁检查、产物从哪里来、谁审批发布。
  3. 对每个关键设计说明替代方案及成本：安全、时效、复杂度和回滚。
  4. 拿出可验证成果：失败用例、构建日志、制品 SHA、回滚演练、监控对照。
  5. 区分“我亲手做过”“我在 demo 中验证过”“我只了解原理”。
