01 · 核心业务页面性能优化

匿名案例｜以消费类 App 首页 / WebView 页面为情境；关联 首屏慢场景、浏览器、构建。

L1–L5
事实卡（先由本人核验）：负责的具体页面/入口；业务目标；当时可使用的 RUM、Network 和 Performance 证据；实际改动清单；可公开的前后对比；个人与团队贡献边界。下方的方案只是候选回答路径。
L1｜你负责的页面为什么需要优化？你的责任边界是什么？
回答要点：说清用户动作、页面构成、受影响人群与目标指标；不要把 DAU 当作性能改善证据。区分本人实现、团队策略和平台能力；先确认优化的是首屏、可交互时间还是点击响应。

追问：“慢”由哪类用户、哪种网络或机型反馈？

L2｜如何证明瓶颈在 JS、资源、接口还是渲染？
回答要点：用真实用户监控确定分布与分群，再在可复现环境用 Network、Performance、Long Tasks、瀑布图定位；关联 TTFB、LCP、资源下载、主线程和业务首屏时机。先区分实验室数据与真实用户数据，避免只看 Lighthouse 总分。

追问：接口耗时不变但 LCP 变差，下一步查什么？

L3｜为什么选择拆包、缓存或延迟加载，而不是先用 CDN？
回答要点：针对瓶颈比较边际收益：关键路径 JS 过大考虑路由级分包与减少初始化；高重复访问考虑有版本管理的缓存；网络传输慢才评估 CDN/压缩。解释拆包增加请求数、过细分包和缓存失效的代价。

追问：公共包缓存命中率下降反而变慢，怎么办？

L4｜拆包与缓存策略落地时，如何防止新旧版本混用？
回答要点：稳定内容 hash 的静态资源采用长缓存，HTML/入口配置采用可及时更新的策略；部署保持旧 hash 文件一段时间，避免在途页面引用失效。异步 chunk 加载错误应有提示、有限重试或刷新恢复；具体缓存头须以部署架构为准。

追问：用户打开旧页面数小时后再切路由，chunk 404 如何恢复？

L5｜如何证明优化有效？若数据没有改善怎么办？
回答要点：统一口径、版本、人群与设备分组，对比 p75/p95 与样本量，监控 JS 错误、崩溃和业务转化的副作用；没有可用前后数字时如实说明验证过程及缺口。无改善则重新核对是否优化了关键路径、是否被接口或第三方资源主导。

追问：实验室改善但真实用户无变化，怎样解释？

面试证据：匿名化性能火焰图、构建前后 chunk 清单、埋点口径、灰度对比记录（均需脱敏且获准公开）。
失分点：堆砌 CDN、gzip、preload；把 FCP 等同业务首屏；把团队指标冒充本人产出；未考虑缓存和发布一致性。
最小实践：使用公开 demo 制造阻塞脚本与大 bundle，记录 Performance / Network → 路由级拆包 → 对比 LCP 与主线程；写清浏览器缓存是否被清空。

02 · 前端监控与白屏治理

匿名案例｜性能、错误、接口、业务异常；关联 白屏排查、浏览器。

L1–L5
事实卡：采集端的真实边界、接入范围、是否自建平台、告警责任人、采样率、脱敏方案及亲自实现部分；未知的覆盖率/降幅留空。
L1｜为什么要做监控？你负责采集、告警还是平台？
先描述业务风险（白屏、错误、关键动作失败）与监控目标；拆清 SDK 接入、平台查询、告警与值班职责。指标至少区分页面性能、JS/资源异常、接口失败和业务异常，不能把“装了 SDK”当作完整治理。
L2｜FCP/LCP/CLS/INP 与业务首屏、白屏如何采集？
Web Vitals 可通过成熟库采集并按其生命周期上报；业务首屏需定义数据就绪与关键区域渲染完成，单靠 mounted 不代表异步数据已绘制。白屏通常需业务容器、关键元素、页面生命周期与错误信号共同判断，不能仅凭 body 为空；注意误报、采样及浏览器兼容。
L3｜为什么监控 SDK 自己不能拖慢页面或泄漏隐私？
控制包体与监听成本、批量/采样发送、离开页面时用适当上报机制；字段白名单和敏感信息脱敏，避免发送 token、用户输入和请求体。上报失败不得影响主流程；对性能指标采用明确来源和采样策略。
L4｜如何把“收到一个白屏告警”变成可定位的事件？
以 release、路由、设备、网络、时间窗口关联 JS 错误、资源失败、接口耗时与发布记录；source map 应安全保存并按权限解析，不宜把可还原源码的映射随意公开。建立去重、阈值和告警归属，先评估影响范围再止损。
L5｜如何验证治理有效，并防止监控代码被误改？
对比告警准确性、故障发现时间、恢复时间及监控自身错误率；权限、CODEOWNERS、强制 Review、测试与灰度共同保护采集链路。若无法提供真实数据，说明希望如何量化而不填造百分比。
面试证据：匿名字段字典、采集时序、告警规则、故障复盘（脱敏）、采样/上报性能测试。
失分点：把 SDK 名称当采集原理；误用 mounted 作为业务首屏；上传敏感字段；只讲采集不讲告警、归因与恢复。
最小实践：在测试页制造 JS 报错、chunk 失败及空白容器，分别采集、关联 release 并手动验证误报。

03 · 灰度发布与功能开关

匿名案例｜配置化功能、渐进放量和回滚；关联 灰度场景、发布专题。

L1–L5
事实卡：真实灰度粒度、分桶主体、配置服务归属、回滚权限、实验指标；“自建 SDK”与“接入既有 SDK”须区分。
L1｜业务为什么不能直接全量发布？
澄清新功能风险、目标人群、观测窗口和止损边界；先说明是发布灰度还是 A/B 实验，两者目标不完全相同。承认浏览器端开关不是安全授权边界。
L2｜怎样保证同一用户稳定命中相同版本？
对实验 ID 与稳定用户标识进行确定性分桶，避免每次 Math.random 导致变组；未登录设备切登录用户、跨设备和 ID 缺失须定义迁移策略。曝光应记录实际看到的变体而非仅分配到变体。
L3｜规则下发失败、版本不一致怎么办？
配置需具备版本号、有效期、缓存及约定默认行为；远程失败时使用仍有效的缓存或安全稳定变体。评估配置更新延迟和正在进行的业务流程是否允许中途切换，重要规则服务端也须执行。
L4｜发现指标异常，kill switch 如何执行并回退？
定义触发条件、负责人和开关传播时间；先关闭有风险变体，必要时执行应用版本回滚或停止入口。Kill switch 只能覆盖受开关控制的功能，数据库变更与客户端缓存可能需要额外回退方案。
L5｜灰度结果怎么判断，不把相关当因果？
定义曝光和业务指标、分母、观测窗口、样本与人群差异；区分实验设计和普通灰度观测。不随意声称某次改善由开关导致，需排查同期发布及网络/设备构成变化。
面试证据：分桶样例、配置版本记录、开关传播测试、匿名化观测报表与回滚演练。
失分点：每次随机分桶；把前端 flag 当权限校验；只缓存不谈过期；kill switch 被说成能撤销所有副作用。
最小实践：实现 10% 稳定分桶，模拟配置服务断线和版本更新，验证同 ID 稳定、失效兜底及紧急关闭。

04 · 播放器或实时交互模块重构

匿名案例｜播放器、WebSocket、权限与埋点；关联 请求与一致性场景、JavaScript。

L1–L5
事实卡：重构前痛点、本人改造的状态或模块、真实接口与播放能力边界、兼容性需求、上线方式。不要把示例状态机冒充既有项目架构。
L1｜原实现的痛点是什么？为什么值得重构？
具体描述状态混乱、重复监听、功能迭代困难或线上缺陷中的实际一种；建立可观察证据（缺陷、回归成本、模块耦合），先说明为何局部修复不够。明确业务不中断的限制。
L2｜你会如何划分播放器状态、事件和副作用？
区分播放域状态（idle/loading/playing/paused/error）、业务权限和 UI 展示；在状态转换处集中处理异步副作用、取消与资源释放。避免多个组件对同一 player 重复订阅而无法清理。
L3｜WebSocket 重连与消息乱序怎么处理？
断线重连采用有上限的指数退避与随机抖动；按业务需要设计心跳、序列号/版本和重同步，不能仅靠“收到消息就覆盖状态”。发送端、接收端重复处理与幂等须明确。
L4｜如何保证权限、支付、登录和播放器模块不互相污染？
拆分边界和接口契约，鉴权由服务端强制执行，前端展示权限只做体验控制；事件订阅统一管理并在卸载时清理。支付回调应服务端确认结果，前端跳转不能作为支付成功凭据。
L5｜重构怎么安全上线，如何证明质量变好？
构建旧新行为对照测试，关注弱网、切后台、断网、切换房间、重复登录、组件销毁等场景；逐步切流并观测播放器失败率、卡顿和资源占用。无法量化时明确只掌握功能回归结果。
面试证据：模块依赖图、状态转换表、订阅清理测试、弱网回归清单（仅可公开版本）。
失分点：只谈代码优雅不谈业务风险；重连无上限；把前端权限当安全措施；忽略事件/定时器清理。
最小实践：用 mock WebSocket 构造断线、乱序、重复消息及组件卸载，验证版本控制与资源释放。

05 · Webpack 构建升级与交付改造

匿名案例｜遗留项目升级、拆包、缓存与回滚；关联 Webpack / Vite、构建专题。

L1–L5
事实卡：升级前后确切版本、为何升级、loader/plugin 兼容问题、构建与产物指标、发布范围；未做过的迁移步骤不得作为个人经历。
L1｜为何升级构建工具，而不是维持现状？
给出维护风险、构建成本、依赖兼容或功能需求中的实际驱动；说明版本边界与业务不能停摆的约束。不要只用“新版本更快”代替问题定义。
L2｜怎样盘点 loader、plugin 和 Node 版本兼容性？
锁定原依赖图，核对目标版本迁移文档、loader/plugin API 和 Node 支持区间；先在独立分支执行原基线构建/测试，再逐项升级记录失败原因。loader 负责模块转换，plugin 参与更广构建生命周期，迁移检查点不同。
L3｜你怎么证明分包与 Tree Shaking 确实生效？
分析构建产物和实际请求，关注入口大小、异步 chunk、重复依赖和无副作用标记；Tree Shaking 的效果受 ESM、sideEffects 与压缩阶段影响。包变小不必然代表用户体验变快，要回到真实加载路径。
L4｜生产发布时如何避免 chunk 404、缓存错配和环境差异？
使用 content hash、保留可被旧页面引用的资源、明确 HTML 缓存策略；同一个构建产物按环境注入必要配置，避免生产/预发重新构建造成不可追溯差异。回滚要能定位到产物与配置版本。
L5｜升级成效与回退标准怎样设定？
比较相同机器和依赖缓存条件下的冷/热构建时间、构建成功率、产物体积与线上错误；分阶段放量，若关键兼容或性能指标退化则按预案退回。真实收益应有可重复测试条件，而非一次截图。
面试证据：升级差异清单、构建日志、bundle 分析、迁移测试、发布与回滚记录。
失分点：混淆 loader/plugin；称拆包必然变快；只报构建速度不看用户指标；忽略历史资源保留。
最小实践：对公开样例实施依赖升级并保持同一构建环境；收集冷/热构建与产物数据，模拟旧页面延迟加载 chunk。

06 · AI 需求分析 / 客服 Agent

学习项目与产品原型情境｜区分已实现、计划中、实验；关联 SSE / 取消生成、TypeScript。

L1–L5
事实卡：明示这是个人实验、原型还是生产系统；核验实际节点、工具、模型、持久化、评测样本和使用者。示例的 HITL / Critic 不代表已上线或自动保证正确。
L1｜为什么这里需要 Agent，而不是普通聊天接口或固定工作流？
先定义用户任务、输入和成功标准；固定流程足够则用工作流，确需基于中间结果选择工具或分支时再引入 Agent。明确延迟、成本、可解释性与故障处理代价；不以“用了 LangGraph”作为业务价值。
L2｜State、Node、条件边、并行与 HITL 如何配合？
State 保存结构化上下文，Node 接受状态并输出更新，边定义流转；多节点并行时设计状态合并与冲突策略；缺失关键需求时通过中断并恢复执行。说明哪些流程真由模型决策、哪些由确定性代码控制。
L3｜Tool Calling 和结构化输出怎样保障可靠性？
用 schema 限定字段并做运行时校验，工具执行要有授权、参数校验、超时、错误分类和幂等；模型可产生不符合 schema 的结果，结构化输出不代表业务事实正确。明确重试次数、补偿和人工接管条件。
L4｜SSE 断线、取消、重复工具调用和旧结果覆盖如何处理？
流式协议按事件边界解析，处理 UTF-8 跨 chunk；以 taskId/version 隔离新旧流，AbortController 取消前端消费不等于后端必定停止。工具副作用设置幂等键，断线续传需要服务端事件记录与去重约定。
L5｜如何评价 Agent 的质量，而不是只展示成功 demo？
建立覆盖典型、模糊、恶意输入与工具失败的用例集；区分结构合法率、任务成功率、人工接管率、延迟、成本与事实依据。Critic 模型只能提供辅助判断，关键输出仍需业务校验或人工验收；报告真实样本数和失败案例。
面试证据：匿名化运行轨迹、节点图、真实测试用例、失败样例、评测定义与成本数据；勿提交真实 API key 或用户对话。
失分点：把工作流统称自主 Agent；认为 schema 保证事实正确；认为 abort 必停服务端；拿模型自评当最终验收。
最小实践：构建含工具超时与 HITL 的 5 条测试输入，记录期望/实际/失败原因，再回归一次版本改动。

可复用项目答题稿（空白模板）

先填写再闭卷复述；「未知」应保留为未知。不要上传公司内部截图、用户数据、密钥或未获授权的指标。

项目：［匿名名称 / 时间范围 / 本人职责］
业务目标：［哪类用户、什么需求］
问题证据：［可公开的指标、复现、日志、截图］
备选方案：［A / B］ 选择依据：［约束与权衡］
实现与难点：［自己写的模块、关键机制、边界］
验证：［基线 / 对照 / 观测窗口 / 副作用］
实际结果：［仅填写经核验、获准公开的数据或定性结果］
反思：［未解决的问题、若重做会如何调整］
个人贡献边界：［自己 / 团队 / 第三方平台］
