#01
Webpack 和 Vite 有什么区别？为什么 Vite 开发阶段更快？
S级 题型：核心原理 刁钻度：★★★★☆ 来源样本：字节 2026 / 好未来 / 中小厂
训练目标：30 秒结论 + 90 秒展开 + 2～3 层追问
版本提醒：旧版 Vite 常见是 esbuild 预构建 + Rollup 生产；当前官方文档已进入 Rolldown 体系。面试优先答架构思想，再注明版本差异。
题目主要考察点和方向概述
1. Webpack 是典型 bundler：从 entry 建依赖图，再产出 bundle。
2. Vite dev 基于浏览器原生 ESM，源码按需转换/提供，不需要启动前先完整 bundle 整个应用。
3. 依赖会预构建并缓存；HMR 基于 ESM 模块图做精准失效。
4. 版本注意：旧版 Vite 常见 esbuild 预构建 + Rollup 生产；当前官方文档已进入 Rolldown 体系。
标准答案
Webpack 和 Vite 最大区别，我会从开发阶段的工作模型讲。 Webpack 是典型静态模块打包器。它从 entry 出发解析依赖，建立 dependency graph，再把模块加工成一个或多个 bundle。传统开发服务启动时往往需要先完成较完整的依赖分析和构建，因此项目越大，冷启动和重构建成本越明显。 Vite 开发阶段不是先把整个应用完整打包，而是利用浏览器原生 ESM。源码模块在浏览器真正请求到时才转换并返回，所以启动时不需要提前处理整棵业务依赖树。对于 node_modules 里稳定、复杂的第三方依赖，Vite 会做 dependency pre-bundling：兼容 CommonJS/UMD，并把过细的依赖模块合并，减少开发服务器请求数，同时做缓存。 HMR 方面，Vite 基于 ESM 模块图做失效传播。某个文件变化时，通常只需要更新到最近 HMR boundary 的链路，不必重新构建整个 bundle，因此大型项目里反馈更稳定。 生产阶段二者都会做真正的打包、Tree Shaking、Code Splitting 等优化。还要注意版本差异：很多旧资料里的“esbuild 预构建 + Rollup 生产”对应旧版 Vite；当前官方文档已经进入 Rolldown 体系。面试最稳的是先讲架构思想，再补项目所用版本。
答案整体解析
不要把“Vite 快”只归因于某个底层工具。最稳定的答案是：dev 不先全量 bundle + native ESM 按需 + 依赖预构建缓存 + 精准 HMR。
高频追问 + 答案
追问 1：Vite 为什么还要预构建依赖？
一是把 CommonJS/UMD 兼容成 ESM；二是把类似 lodash-es 这种大量小模块依赖合并，避免浏览器产生数百个请求。
追问 2：Vite 是不是完全不打包？
不是。开发源码主要按 ESM on-demand 提供，但依赖会预构建；生产环境仍会 bundle。
追问 3：为什么很多资料还说 Vite 用 esbuild + Rollup？
那是旧版本的典型实现。当前 Vite 官方文档已经演进到 Rolldown，所以面试要说明版本。
追问 4：Vite 项目越大启动时间就完全不变吗？
不能绝对化。插件、依赖扫描、业务配置仍会影响启动，只是避免了传统全应用 eager bundle 的主要扩张成本。
失分点 / 易错点
常见失分：只回答“Vite 用 esbuild，所以快”，既浅又容易因版本升级过时。
记忆钩子
Webpack：先建图再 bundle；Vite dev：源码按需 ESM + 依赖预构建 + 精准 HMR。
前置知识 / 关联知识
前置：ESM、dependency graph、bundle。关联：HMR、pre-bundling、Rolldown。
#02
Webpack 的完整构建流程是什么？
S级 题型：核心原理 刁钻度：★★★★☆ 来源样本：高级前端高频
训练目标：30 秒结论 + 90 秒展开 + 2～3 层追问
题目主要考察点和方向概述
1. 初始化：读取配置、创建 Compiler、注册 Plugin。
2. Entry 开始：resolve → loader transform → parse dependencies → 递归建立 Module Graph。
3. 根据 entry、动态 import、SplitChunks 等组织 Chunk / Chunk Graph。
4. 优化、代码生成、hash、生成 assets，最后 emit 到 output。
标准答案
Webpack 构建流程我会分五层。 第一步初始化：读取配置和命令行参数，创建 Compiler，并执行插件的 apply，让 Plugin 注册到生命周期 hooks。 第二步从 entry 开始构建模块图。Webpack resolve 模块路径，匹配 module.rules，对模块应用 Loader 转换，再解析转换后的源码，找出 import、require、动态 import 等依赖，递归处理，最终形成 Module Graph。 第三步组织 Chunk。Webpack 根据 entry、动态 import、SplitChunks 等规则，把模块组织成一个或多个 chunk，并建立 chunk 关系。 第四步优化和代码生成，包括 module/chunk 优化、Tree Shaking、runtime 生成、hash、压缩等，形成待输出 assets。 第五步 emit，把 JS/CSS/图片等资源写入 output 目录。整个过程中 Plugin 可通过 Compiler / Compilation hooks 介入解析、优化、生成、emit 等阶段。
答案整体解析
高级面试最好能区分 Module Graph 和 Chunk Graph：前者描述源码依赖，后者描述最终如何成为加载单元。
高频追问 + 答案
追问 1：Loader 在什么时候执行？
模块 resolve 后、加入最终依赖图前，需要先通过匹配的 Loader 转成 Webpack 可继续处理的模块内容。
追问 2：Module 和 Chunk 是一回事吗？
不是。Module 是源码依赖单元；Chunk 是打包/加载单元，一个 chunk 可包含多个 modules。
追问 3：Compiler 和 Compilation 区别？
Compiler 代表整体编译器生命周期；Compilation 更接近某一次具体构建产生的模块、chunk、assets 状态。
追问 4：动态 import 改变了什么？
它形成异步依赖边界，使相关模块有机会生成独立 async chunk。
失分点 / 易错点
常见失分：只回答“解析、打包、输出”，没有 Module Graph、Chunk、Plugin hooks。
记忆钩子
Config/Plugin → Entry → Resolve/Loader → Module Graph → Chunk → Optimize → Assets → Emit。
前置知识 / 关联知识
前置：模块系统、AST。关联：Loader/Plugin、SplitChunks、Tree Shaking。
#03
Loader 和 Plugin 有什么区别？
S级 题型：API完整性 刁钻度：★★★★☆ 来源样本：社招高频
训练目标：30 秒结论 + 90 秒展开 + 2～3 层追问
题目主要考察点和方向概述
1. Loader：模块级转换器，把某类输入转换成 Webpack 能继续处理的 module。
2. Plugin：基于 Compiler/Compilation hooks 扩展整个构建生命周期。
3. Loader 通过 module.rules 匹配；Plugin 通常通过 new XxxPlugin() 注册。
4. 追问：Loader 链顺序、pitch、Plugin apply/hook。
标准答案
Loader 和 Plugin 最大区别可以记成：Loader 解决“一个模块怎么转换”，Plugin 解决“整个构建过程怎么扩展”。 Loader 主要处理模块内容。Webpack 遇到匹配 module.rules 的文件后，会按 loader 链转换输入，例如 JS/TS、CSS、资源等，最终让这些内容纳入依赖图。它本质更像模块级 transform。 Plugin 范围更广。Plugin 通过 apply(compiler) 注册到 Compiler / Compilation hooks，可以参与依赖解析、chunk 优化、资源生成、环境变量注入、进度输出、emit 等多个生命周期阶段。 所以更准确的表达是：Loader 面向 module transformation，Plugin 面向 lifecycle/build extension。
答案整体解析
不要只背“Loader 处理文件，Plugin 做插件”。面试官通常会继续问执行阶段和为什么某能力必须做成 Plugin。
高频追问 + 答案
追问 1：Loader 链顺序是什么？
normal 阶段通常从右到左/从下到上执行；还存在 pitch 阶段，顺序相反。
追问 2：Loader 能异步吗？
可以，通过 Loader API 如 this.async() 返回异步结果。
追问 3：Plugin 最核心的方法？
通常实现 apply(compiler)，在里面对相应 hook 使用 tap/tapAsync/tapPromise 注册逻辑。
追问 4：为什么抽 CSS 常需要 Plugin？
跨模块收集 CSS 并生成独立 asset 涉及整个 Compilation/asset 生命周期，不只是单模块转换。
失分点 / 易错点
常见失分：没有说明作用范围和生命周期机制。
记忆钩子
Loader 改 module；Plugin 改 build。
前置知识 / 关联知识
前置：Webpack流程。关联：Tapable、Compiler/Compilation、CSS处理。
#04
SplitChunks 的作用是什么？核心参数有哪些？
S级 题型：分包 刁钻度：★★★★☆ 来源样本：高级高频
训练目标：30 秒结论 + 90 秒展开 + 2～3 层追问
题目主要考察点和方向概述
1. 目标：抽共享模块、控制 chunk 大小和请求模型，提高复用与缓存。
2. 核心：chunks、minSize、minChunks、maxAsyncRequests、maxInitialRequests。
3. cacheGroups 常用 test、priority、reuseExistingChunk、name 等做 vendor/common 分组。
4. 不要死背默认值；配置与 Webpack 版本、HTTP 模型和业务体积相关。
标准答案
SplitChunksPlugin 的作用，是根据模块复用情况、chunk 大小和请求数量，把模块重新组织到更合适的 chunk 中。 chunks 决定处理 async、initial 还是 all；minSize 控制候选拆分达到多大才值得单独成 chunk；minChunks 表示至少被多少 chunk 复用才满足公共模块抽取条件。 maxInitialRequests 和 maxAsyncRequests 分别限制初始加载和异步加载时允许的并行 chunk 请求数量，本质是在“拆细提高复用/缓存”和“避免请求过多”之间做平衡。 cacheGroups 是业务最常用的分组能力，例如把 node_modules 公共依赖放 vendor，把多 chunk 共享模块放 common，常配 test、priority、minChunks、reuseExistingChunk、name。 工程里不要追求 bundle 越小越好，要结合首屏请求数、缓存命中率、HTTP 版本、路由粒度和真实性能验证。
答案整体解析
你之前拆包回答偏技术清单，这里要先讲为什么拆，再讲参数，再讲 tradeoff。
高频追问 + 答案
追问 1：maxInitialRequests 和 maxAsyncRequests 区别？
前者约束初始页面加载 chunk 请求数量，后者约束动态 import 等异步加载场景的请求数量。
追问 2：cacheGroups priority 干什么？
模块可能同时匹配多个 group，priority 决定优先进入哪个组。
追问 3：为什么拆包过细会变慢？
请求调度、header、解析执行、runtime 都有成本；最佳粒度取决于网络协议和设备。
追问 4：vendor 包是不是越大越稳定越好？
不是。超大 vendor 任一依赖升级都可能导致整体 hash 变化，应按更新频率和复用情况设计。
失分点 / 易错点
常见失分：背参数但不会解释参数为什么存在，也没有验证指标。
记忆钩子
SplitChunks = 复用 + 体积 + 请求数三者平衡。
前置知识 / 关联知识
前置：Chunk、缓存、HTTP并发。关联：dynamic import、contenthash。
#05
动态 import / Code Splitting 怎么工作？
S级 题型：分包 刁钻度：★★★★☆ 来源样本：高频
训练目标：30 秒结论 + 90 秒展开 + 2～3 层追问
题目主要考察点和方向概述
1. import() 是异步模块边界，返回 Promise。
2. Webpack 构建时可生成独立 async chunk，运行时需要时再加载。
3. 路由懒加载、重型低频功能是典型场景。
4. 注意 chunk load error、waterfall、预加载与缓存。
标准答案
Code Splitting 的核心是把一次性加载的代码拆成多个可独立加载的 chunk。 Webpack 中动态 import() 是最常见的异步拆分边界。构建时 Webpack 识别 import() 指向的依赖，把相关模块组织成独立 async chunk；运行时真正执行到 import() 时，Webpack runtime 再发网络请求加载 chunk，完成模块注册后 Promise resolve。 路由懒加载最典型。富文本、图表、PDF、3D 编辑器等低频重功能也适合按功能懒加载。 但 Code Splitting 不是拆了就一定快。要避免过深 waterfall、过多小 chunk，并考虑 ChunkLoadError、版本发布兼容和高概率资源预加载。
答案整体解析
面试里最好同时讲“构建时怎么拆”和“运行时怎么加载”。
高频追问 + 答案
追问 1：import() 和静态 import 区别？
静态 import 在模块解析阶段确定依赖；动态 import() 是运行时触发的异步边界并返回 Promise。
追问 2：懒加载为什么可能点击后卡一下？
交互时才产生 RTT、下载、parse/compile/execute，可对高概率路径预加载。
追问 3：ChunkLoadError 怎么处理？
可做错误提示/重试/刷新兜底，部署上避免新 HTML 引用的旧 chunk 被立即清理。
追问 4：Webpack runtime 做什么？
维护模块/chunk 注册和加载逻辑，根据 chunk id/publicPath 获取对应资源。
失分点 / 易错点
常见失分：只会回答“import() 可以懒加载”。
记忆钩子
Build：import() → async chunk；Run：执行到 import() → 加载 → Promise resolve。
前置知识 / 关联知识
前置：ESM、Promise。关联：路由懒加载、SplitChunks、prefetch。
#06
Tree Shaking 的原理和前提是什么？
S级 题型：产物优化 刁钻度：★★★★☆ 来源样本：高频
训练目标：30 秒结论 + 90 秒展开 + 2～3 层追问
题目主要考察点和方向概述
1. 依赖 ESM 静态结构做 import/export usage analysis。
2. Webpack 标记 used/unused exports，生产优化/压缩阶段删除 dead code。
3. sideEffects 帮助判断整个模块是否可安全移除。
4. CommonJS 动态性强，不利于可靠静态分析。
标准答案
Tree Shaking 可以理解为基于静态模块关系做未使用代码消除。 它通常依赖 ES Module，因为 import/export 在构建时更容易静态分析。Webpack 会分析哪些 exports 被使用并标记 unused exports；在 production 优化和压缩阶段，再删除能够确认无副作用的 dead code。 一个关键前提是不能随便删除有副作用的模块，例如 import './global.css'、polyfill、全局补丁。package.json 的 sideEffects 字段可以帮助 Webpack 判断哪些文件可以安全整模块裁剪。 另外如果 Babel 提前把 ESM 转成 CommonJS，Webpack 的静态分析能力会受影响。 所以 Tree Shaking 不是“没 import 就删”，而是静态分析 + usage marking + 副作用判断 + dead code elimination。
答案整体解析
Tree Shaking 高频追问通常就在 ESM、sideEffects 和 Babel 配置。
高频追问 + 答案
追问 1：为什么 ESM 更适合 Tree Shaking？
import/export 结构静态；CommonJS 的 require/exports 更动态，构建期更难可靠确定依赖。
追问 2：sideEffects:false 是什么意思？
声明模块默认没有导入即执行副作用，可更大胆删除未使用整个模块；CSS/polyfill 等需白名单保留。
追问 3：unused export 在哪里真正删掉？
Webpack 先做使用情况分析/标记，最终 production minifier/优化阶段删除对应 dead code。
追问 4：Babel 为什么可能让 Tree Shaking 失效？
若先把 ESM 转 CommonJS，就破坏了原本清晰的静态模块结构。
失分点 / 易错点
常见失分：只回答“删除没用代码”，不提 ESM 和副作用。
记忆钩子
ESM 静态分析 → 标 used → 判断 sideEffects → 删除 dead code。
前置知识 / 关联知识
前置：ESM/CommonJS。关联：Babel、production mode、sideEffects。
#07
Webpack 怎么优化构建速度？
S级 题型：工程化 刁钻度：★★★★☆ 来源样本：社招高频
训练目标：30 秒结论 + 90 秒展开 + 2～3 层追问
题目主要考察点和方向概述
1. 先测：profile/stats/构建日志看慢在哪里。
2. 少做：缩小 Loader 范围、减少无效 resolve、减少重插件。
3. 缓存：Webpack 5 filesystem cache + 工具自身缓存。
4. 并行/替换工具：thread-loader 要算成本；SWC/esbuild/Rspack 等按项目评估。
5. 最后用 cold/warm build、rebuild 时间验证。
标准答案
Webpack 构建速度优化，我会按“定位 → 减少工作量 → 缓存 → 并行/替换工具 → 验证”回答。 先用 stats、profile、构建日志或分析工具确认是 Babel/TS 慢、某个 Loader/Plugin 慢、依赖解析慢还是压缩慢。 然后减少无效工作：Loader 用 include/exclude 缩小范围，避免无意义扫描 node_modules；减少 resolve.extensions 等搜索尝试；开发环境关闭不必要的 production 压缩和重型分析插件。 再利用缓存。Webpack 5 的 filesystem cache 能显著减少二次构建重复工作；部分转译工具也有自身缓存。 最后才考虑并行和更快工具。thread-loader 有 worker 启动和 IPC 成本，并非越多越快；纯转译场景可评估 SWC/esbuild，工程允许时也可评估 Rspack/Vite。 最终固定环境比较 cold build、warm build、单文件 rebuild/HMR 时间，而不是凭感觉判断。
答案整体解析
这是典型工程回答：先诊断，再方案，再验证。不能只列 cache/thread-loader。
高频追问 + 答案
追问 1：thread-loader 为什么不一定越多越快？
worker 启动、序列化、IPC 有成本，只有单任务 CPU 工作足够重时才可能获益。
追问 2：为什么 node_modules 常排除 Babel？
第三方包多且大，多数已有可运行产物，全量再次转译成本高；少数现代依赖再按兼容目标处理。
追问 3：filesystem cache 的意义？
持久化可复用构建结果，依赖/config 未变化时避免重复计算。
追问 4：怎么证明优化有效？
固定机器、Node、缓存条件，多次记录 cold/warm/rebuild 的 P50/P95 进行前后对比。
失分点 / 易错点
常见失分：一上来报 thread-loader、cache，没有定位场景，也没有验证。
记忆钩子
先 Profiling，再少做、缓存、并行/换工具，最后量化。
前置知识 / 关联知识
前置：Webpack流程。关联：CI、cache、SWC/Rspack/Vite。
#08
Webpack 怎么优化产物体积和首屏加载？
S级 题型：工程化 刁钻度：★★★★☆ 来源样本：社招高频
训练目标：30 秒结论 + 90 秒展开 + 2～3 层追问
题目主要考察点和方向概述
1. 先分析：stats / Bundle Analyzer 找大模块、重复依赖、首屏低频代码。
2. 减总量：Tree Shaking、按需引入、替换重库、压缩、移除重复/无用代码。
3. 调时机：路由/功能 lazy、SplitChunks、合理 vendor/common。
4. 传输缓存：contenthash、长缓存、CDN、Brotli/gzip、谨慎 preload/prefetch。
5. 用 LCP/FCP、JS transfer/parse/execute、waterfall 验证。
标准答案
产物优化我会分成“发现问题 → 减少总量 → 调整加载时机 → 提升传输缓存 → 指标验证”。 先通过 stats、Bundle Analyzer 找最大 chunk、重复依赖和首屏加载的低频模块，确认到底是总量太大还是首屏加载太多。 减少总量：用 ESM + Tree Shaking 删除未使用代码；组件库/工具库按需引入；检查重复版本、超大 locale/polyfill；生产压缩；必要时换轻量依赖。 调整加载时机：路由和低频重功能用动态 import 懒加载；SplitChunks 抽真正共享依赖，同时避免一个超大 vendor 包。 传输缓存：静态资源 contenthash + 长缓存，配 CDN、Brotli/gzip；preload 只给真正关键资源，prefetch 给低优先级未来可能用的资源。 最后不能只看 dist 从 5MB 变 3MB，还要看首屏 transferred JS、waterfall、JS parse/execute、FCP/LCP、Long Task。用户真正感知的是加载和交互。
答案整体解析
这题正好把“优化技术清单”升级成完整工程链路。
高频追问 + 答案
追问 1：bundle 变小为什么 LCP 可能不变？
减少的可能是非首屏 chunk，或瓶颈在图片、TTFB、主线程而非 JS 下载。
追问 2：preload 是不是越多越好？
不是。它会提高优先级，滥用会和真正关键资源争带宽。
追问 3：为什么拆包后首屏可能更慢？
过多关键请求、依赖 waterfall、runtime 开销或错误公共依赖拆分都会拖慢。
追问 4：第三方超大依赖怎么处理？
先看能否 Tree Shake/按需引入/轻量替代，再决定异步拆分或 external/CDN，并评估缓存和稳定性。
失分点 / 易错点
常见失分：说了 CDN/gzip/preload 等一堆方案，却没有先定位、取舍和验证。
记忆钩子
分析 → 减总量 → 延后非关键 → 缓存传输 → 用户指标验证。
前置知识 / 关联知识
前置：SplitChunks、Tree Shaking、HTTP缓存。关联：FCP/LCP、CDN、压缩。
