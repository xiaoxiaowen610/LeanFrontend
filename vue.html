#01
Vue2 和 Vue3 的响应式原理分别是什么？
S级 题型：核心原理 刁钻度：★★★★☆ 来源样本：编程猫社招 / 雪球 / 好未来 / 中小厂
训练目标：30 秒结论 + 90 秒展开 + 2～3 层追问
题目主要考察点和方向概述
1. Vue2：Object.defineProperty 如何拦截已有对象属性的 get / set。
2. Vue3：Proxy 代理整个对象，配合 Reflect、track / trigger 做依赖收集和触发。
3. 重点对比：新增/删除属性、数组、Map/Set、初始化成本、原对象与代理对象的关系。
标准答案
Vue2 的核心是通过 Object.defineProperty 给 data 中已经存在的属性定义 getter / setter。组件渲染时读取属性会完成依赖收集，属性修改时 setter 再通知对应 watcher 更新。它的问题是只能劫持“已经定义好的属性”，新增或删除属性需要额外 API；数组也需要对变更方法做特殊处理。 Vue3 改成 Proxy。reactive() 返回原对象的代理对象，Proxy 可以统一拦截 get、set、deleteProperty、has、ownKeys 等操作，再通过 track / trigger 建立依赖和触发副作用。它能够更自然地处理属性新增删除、数组索引和 length，以及 Map、Set 等集合类型。 所以面试里不要只说“Vue3 用 Proxy 更快”，更准确的是：Vue3 的响应式能力更完整，拦截粒度更统一，而且是按访问进行深层代理；真正的更新性能还要结合编译期的 PatchFlag、静态缓存和 Block Tree 一起看。
答案整体解析
这题同时考“响应式机制”和“不要把响应式优化与编译优化混为一谈”。Vue3 的 Proxy 主要改善的是可观测能力与实现方式；Vue3 运行时更新效率高，还来自 compiler-informed VDOM。
高频追问 + 答案
追问 1：Vue2 为什么检测不到对象新增属性？
因为 defineProperty 是对已有 key 单独定义 getter/setter，新 key 没有被预先劫持。Vue2 通常需要 Vue.set / this.$set。
追问 2：Vue2 数组为什么要重写 push/splice 等方法？
直接监听数组每个索引成本和语义都不理想，所以 Vue2 对一组会改变数组的方法做了包装，调用后主动通知依赖。
追问 3：Vue3 reactive 为什么原对象修改不会触发更新？
响应式连接建立在 Proxy 上。reactive(raw) 返回 proxy，raw !== proxy；直接绕过 proxy 修改 raw，就不会经过代理拦截。
追问 4：Proxy 是不是一定比 defineProperty 性能更好？
不能绝对化。Proxy API 更完整、实现更统一，但具体性能取决于场景。Vue3 整体更新性能优势不能只归因于 Proxy。
失分点 / 易错点
常见失分：只回答“Vue2 defineProperty，Vue3 Proxy”，却说不清为什么换、解决什么、不能解决什么。
记忆钩子
Vue2：逐属性 defineProperty；Vue3：整对象 Proxy。响应式完整性 ≠ 编译优化。
前置知识 / 关联知识
前置：getter/setter、Proxy、Reflect、依赖收集。关联：ref/reactive、effect、Vue3 编译优化。
#02
Proxy 相比 Object.defineProperty 解决了哪些问题？
S级 题型：核心原理 刁钻度：★★★★☆ 来源样本：货拉拉 / 多家公司
训练目标：30 秒结论 + 90 秒展开 + 2～3 层追问
题目主要考察点和方向概述
1. defineProperty 是属性级拦截；Proxy 是对象级代理。
2. 重点：新增/删除属性、数组索引与 length、in / Object.keys、Map/Set 等。
3. 边界：Proxy 返回新代理对象；无法 polyfill 到 IE 这类老环境。
标准答案
Proxy 最大的变化不是“语法更简洁”，而是它能代理对象层面的多种操作。Object.defineProperty 主要针对某个已有属性的 getter/setter，因此新增属性、删除属性、数组索引等场景需要额外处理。 Proxy 可以通过 set 拦截新增和修改，通过 deleteProperty 拦截删除，通过 has、ownKeys 等处理 in 和属性枚举，也能在 Vue3 的响应式体系中支持 Map、Set 等集合类型。数组也不需要像 Vue2 那样单独依赖一套数组变更方法补丁。 同时要知道，reactive() 返回的是 Proxy，不等于原对象；Proxy 本身也不能像普通库那样完全 polyfill 到不支持它的旧浏览器。
答案整体解析
回答这题最好从“拦截能力”展开，而不是泛泛说 Proxy 性能好。面试官真正想听的是 defineProperty 的能力边界。
高频追问 + 答案
追问 1：Proxy 能拦截哪些典型操作？
常见有 get、set、deleteProperty、has、ownKeys 等。
追问 2：为什么 Vue3 可以直接监听数组下标？
因为数组也是对象，通过 Proxy 的 get/set 等 trap 可以拦截索引和 length 相关操作。
追问 3：Reflect 为什么经常和 Proxy 一起用？
Reflect 提供与对象内部操作更一致的默认语义，Proxy trap 中可用 Reflect.get/set 等完成默认行为，并正确传递 receiver。
失分点 / 易错点
常见失分：回答“Proxy 可以监听新增属性”后就结束，没有说明 delete、数组、集合类型与对象级代理。
记忆钩子
defineProperty：盯属性；Proxy：代理对象操作。
前置知识 / 关联知识
前置：Object.defineProperty、Proxy traps、Reflect。关联：reactive、数组响应式、Map/Set。
#03
ref 和 reactive 有什么区别？为什么 ref 需要 .value？
S级 题型：核心API 刁钻度：★★★★☆ 来源样本：公开高频
训练目标：30 秒结论 + 90 秒展开 + 2～3 层追问
题目主要考察点和方向概述
1. ref 可保存任意类型；reactive 主要用于对象/数组/Map/Set 等对象类型。
2. ref 通过 .value getter/setter 提供稳定的拦截点；对象值内部仍会转成深层响应式。
3. reactive 的局限：不能直接装 primitive；替换整个引用、解构 primitive 属性时容易丢失响应性。
标准答案
ref 和 reactive 都是 Vue3 声明响应式状态的 API。ref 可以保存基本类型，也可以保存对象；它返回一个带 value 属性的 ref 对象。reactive 则直接返回对象的 Proxy，主要用于对象、数组、Map、Set 等对象类型。 ref 为什么需要 .value？因为 JavaScript 无法拦截一个普通局部变量本身的读取和赋值，所以 Vue 把值包装到一个对象属性 value 上，在 getter 中 track，在 setter 中 trigger。模板中 Vue 会做 ref 自动解包，所以通常不用写 .value，但在 JavaScript 中要写。 reactive 的一个重要局限是需要保持同一个 Proxy 引用：整体替换变量，或者把其中的 primitive 属性直接解构出来，都可能让响应式连接断开。因此现在 Vue 官方文档也更推荐把 ref 作为声明响应式状态的主要 API。
答案整体解析
这题不能只答“ref 基本类型、reactive 对象”，因为 ref 也能放对象，而且对象会被深层转换。真正的差异还包括包装方式、替换引用、解构和传递能力。
高频追问 + 答案
追问 1：ref 里放对象后还是响应式的吗？
是。非原始值通常会通过 reactive 转为深层响应式对象，除非使用 shallowRef。
追问 2：reactive 解构为什么会丢响应式？
例如 const { count } = state，得到的是普通 number，不再通过 state.count 的 Proxy get/set 访问。可用 toRefs/toRef 等方式保留连接。
追问 3：模板为什么不用 .value？
模板渲染上下文会对顶层 ref 做自动解包，但数组/Map 中的 ref 等存在额外注意事项。
追问 4：什么时候用 shallowRef？
大型不可变数据、第三方状态对象，或只希望追踪 .value 整体替换而不深度代理内部结构时。
失分点 / 易错点
常见失分：说“ref 只能基本类型、reactive 只能对象”，这是不准确的。
记忆钩子
ref = 值盒子；reactive = 对象 Proxy。JS 用 .value，模板多数自动解包。
前置知识 / 关联知识
前置：Proxy、getter/setter。关联：toRef/toRefs、shallowRef、triggerRef。
#04
Vue 数据变化后，视图更新的完整链路是什么？
S级 题型：核心原理 刁钻度：★★★★☆ 来源样本：高级前端高频
训练目标：30 秒结论 + 90 秒展开 + 2～3 层追问
题目主要考察点和方向概述
1. 首次渲染：render 作为响应式 effect 执行，并 track 依赖。
2. 状态修改：setter / Proxy trap 触发 trigger，找到订阅该依赖的 effect。
3. 调度：组件更新任务进入 scheduler 队列，批量去重，在 next tick 中 flush。
4. 重新 render → 新 vnode → patch/diff → 最小化 DOM 更新。
标准答案
我会把 Vue 的更新链路分成四步。 第一步是依赖建立。组件首次渲染时，render 函数作为响应式 effect 执行，读取 ref/reactive 数据时会 track，把当前组件的更新 effect 与这些依赖关联起来。 第二步是触发更新。状态修改后，会经过 ref 的 setter 或 reactive Proxy 的 set 等拦截，trigger 找到依赖这个状态的 effect。 第三步不是立刻同步重复更新 DOM，而是通过 scheduler 把组件更新任务加入队列并做批量、去重处理。同一个 tick 内多次修改状态，通常只触发必要的组件更新。 第四步重新执行 render，产生新的 vnode 树，renderer 根据 patch/diff 结果更新真实 DOM。Vue3 还会利用编译器提供的 PatchFlag、静态缓存和 Block Tree，只遍历更有可能变化的动态节点。 所以状态变化不是“直接改 DOM”，而是：响应式触发 → 调度 → render → vnode patch → DOM。
答案整体解析
这是把响应式、调度器、VDOM、编译优化串起来的一道高级基础题。答到完整链路，比单独背 Proxy 或 Diff 更体现体系。
高频追问 + 答案
追问 1：为什么 state 改了以后马上读 DOM 还是旧值？
因为 DOM 更新被批量缓冲到 next tick；状态值已经变了，但 DOM patch 尚未 flush 完成。
追问 2：同一个 tick 修改 count 三次，会渲染三次吗？
通常组件更新任务会被 scheduler 去重并批量执行，不是每次赋值都立即做完整 DOM 更新。
追问 3：computed / watch 也属于 effect 吗？
底层都建立在响应式 effect / 依赖追踪体系之上，但调度和语义不同。
失分点 / 易错点
常见失分：只回答“数据变了触发 diff”，中间缺少依赖收集和调度队列。
记忆钩子
track → trigger → scheduler → render → patch → DOM。
前置知识 / 关联知识
前置：Vue响应式、effect、VDOM。关联：nextTick、PatchFlag、scheduler。
#05
Vue 生命周期有哪些？Vue2/Vue3 有什么变化？
S级 题型：API完整性 刁钻度：★★★★☆ 来源样本：公开高频
训练目标：30 秒结论 + 90 秒展开 + 2～3 层追问
题目主要考察点和方向概述
1. 按创建/挂载/更新/卸载四阶段组织，不要零散背。
2. Vue3 Composition API：onBeforeMount/onMounted/onBeforeUpdate/onUpdated/onBeforeUnmount/onUnmounted 等。
3. Options API 与 Vue2 最大命名变化：beforeDestroy/destroyed → beforeUnmount/unmounted。
4. 补充 activated/deactivated、errorCaptured 等特殊钩子。
标准答案
Vue 生命周期我一般按阶段记。 创建阶段，Options API 有 beforeCreate、created；Composition API 中 setup 本身承担了大部分创建阶段逻辑，没有对应的 onBeforeCreate / onCreated。 挂载阶段有 beforeMount / mounted，对应 Composition API 的 onBeforeMount / onMounted。 更新阶段有 beforeUpdate / updated，对应 onBeforeUpdate / onUpdated。 卸载阶段 Vue3 叫 beforeUnmount / unmounted，对应 onBeforeUnmount / onUnmounted；Vue2 这里叫 beforeDestroy / destroyed。 另外 keep-alive 组件还有 activated / deactivated；错误捕获有 errorCaptured / onErrorCaptured。实际工程里 mounted 常用于依赖 DOM 的初始化，unmounted 要清理手动创建的 timer、事件监听、Observer、WebSocket 等副作用。
答案整体解析
水滴已经证明“生命周期完整性题”不能只准备组件主流程。回答时先四阶段，再补特殊钩子，既完整又不啰嗦。
高频追问 + 答案
追问 1：父子组件 mounted / updated / unmounted 顺序？
要结合渲染和卸载过程理解，面试中建议分具体阶段说明，不要死记一条覆盖所有钩子的口令。Vue 官方明确 updated 时父组件 updated 在子组件之后。
追问 2：为什么 updated 里不建议直接改响应式状态？
很容易再次触发更新，造成无限更新循环。
追问 3：何时用 nextTick，而不是 onUpdated？
如果只想等待某次特定状态修改后的 DOM 更新，用 nextTick 更精确；onUpdated 可能由多种状态变化触发。
追问 4：setup 里创建的 watcher 卸载时需要手动 stop 吗？
同步在 setup 中创建并绑定组件实例的响应式 effect 通常会随组件卸载停止；手动创建的外部副作用仍需清理。
失分点 / 易错点
常见失分：只会背 mounted/beforeUnmount，无法按阶段完整展开，也说不出 Vue2→Vue3 命名变化。
记忆钩子
创建 → 挂载 → 更新 → 卸载；Vue3 destroy 改 unmount。
前置知识 / 关联知识
前置：组件挂载流程。关联：nextTick、keep-alive、自定义指令生命周期。
#06
nextTick 是什么？为什么更新 DOM 后经常要 nextTick？
S级 题型：核心原理 刁钻度：★★★★☆ 来源样本：雪球
训练目标：30 秒结论 + 90 秒展开 + 2～3 层追问
题目主要考察点和方向概述
1. Vue DOM 更新是异步批量调度，而不是每次状态改变马上同步 patch DOM。
2. nextTick 用于等待当前批次 DOM 更新 flush 完成。
3. 不要误解成 setTimeout；它是 Vue 调度器提供的“下一个 DOM 更新周期完成后”语义。
标准答案
nextTick 的核心作用，是等待 Vue 当前这一批响应式状态变化对应的 DOM 更新完成。 当我们修改响应式数据时，JavaScript 状态本身会立刻变化，但 Vue 为了批量更新、去重和避免重复渲染，不会每次赋值都同步 patch DOM，而是把更新缓冲到当前 tick 的调度队列里。 所以如果我刚修改 count，马上读取依赖 count 的 DOM，可能还是旧 DOM。await nextTick() 之后再读取，就能拿到本轮 Vue 更新完成后的 DOM。 它不是简单等价于 setTimeout(0)。从面试角度，更应该把它理解为 Vue scheduler 暴露出来的“等待当前更新队列 flush”的 API。
答案整体解析
用户之前已经追问过“为什么 mounted 不够、异步数据渲染后为什么 nextTick + rAF”。这里基础题先讲清 nextTick 的职责，不把它和浏览器真正完成绘制混为一谈。
高频追问 + 答案
追问 1：nextTick 之后浏览器一定已经把像素画到屏幕了吗？
nextTick 保证 Vue 的 DOM patch 已完成，但不等于浏览器已经完成下一帧绘制。若要测实际绘制后的时机，常再结合 requestAnimationFrame。
追问 2：为什么 Vue 要批量更新？
避免同一 tick 多次状态修改导致重复 render/patch，提高更新效率。
追问 3：nextTick 底层是不是 Promise.then？
实现会利用微任务等机制调度，但面试重点应是 scheduler flush 语义，而不是把 API 简化成某一种宿主实现。
失分点 / 易错点
常见失分：回答“nextTick 就是下一个事件循环”或“就是 setTimeout”，都过于粗糙。
记忆钩子
状态先变，DOM 后批量 patch；nextTick = 等这批 DOM 更新完成。
前置知识 / 关联知识
前置：Event Loop、Vue scheduler。关联：mounted、requestAnimationFrame、业务首屏采集。
#07
computed 和 watch 有什么区别？分别适合什么场景？
S级 题型：核心API 刁钻度：★★★★☆ 来源样本：公开高频
训练目标：30 秒结论 + 90 秒展开 + 2～3 层追问
题目主要考察点和方向概述
1. computed：声明派生状态，getter 应保持纯计算，有缓存。
2. watch：观察数据变化并执行副作用，可获得新旧值、控制 immediate/deep/flush。
3. watchEffect：自动收集回调中访问的响应式依赖。
标准答案
computed 和 watch 的核心区别是“派生状态”和“副作用”。 computed 适合根据已有响应式状态计算一个新值，例如总价、过滤后的列表。它会追踪依赖，并对计算结果做缓存：依赖没变，多次读取不需要重新计算。computed getter 应该保持纯计算，不应该在里面发请求、改 DOM 或修改其他状态。 watch 更适合“某个状态变化后我要做一件事”，例如请求接口、写 localStorage、埋点、联动外部系统等。它可以明确指定监听源，还能拿新旧值，并配置 immediate、deep、flush 等。 如果依赖本身不想手动列出来，且副作用里读到哪些响应式数据就监听哪些，可以考虑 watchEffect。
答案整体解析
面试时只说 computed 有缓存、watch 没缓存不够。更稳的主线是：computed = derived state；watch = side effect。
高频追问 + 答案
追问 1：computed 可以有 setter 吗？
可以创建 writable computed，提供 get 和 set；但普通 computed 默认只读。
追问 2：watch 的 flush 有什么作用？
用于控制 watcher 回调相对于组件更新的调度时机，如 pre、post、sync；涉及 DOM 时尤其要理解执行时机。
追问 3：deep watch 为什么可能有性能问题？
需要遍历/追踪深层结构，数据规模大时成本明显，应尽量缩小监听范围。
追问 4：watchEffect 和 watch 最大区别？
watch 明确声明依赖并能拿新旧值；watchEffect 自动收集同步执行过程中读取的依赖，更方便但依赖来源没那么显式。
失分点 / 易错点
常见失分：只背“computed 有缓存”，却讲不出派生状态与副作用的设计边界。
记忆钩子
computed 算值；watch 做事。
前置知识 / 关联知识
前置：响应式 effect。关联：watchEffect、flush、nextTick。
#08
Vue 组件通信方式有哪些？
S级 题型：API完整性 刁钻度：★★★★☆ 来源样本：北京中小厂 / 公开高频
训练目标：30 秒结论 + 90 秒展开 + 2～3 层追问
题目主要考察点和方向概述
1. 父子：props / emits、v-model、template ref（谨慎）。
2. 跨层级：provide / inject。
3. 共享状态：Pinia/Vuex。
4. 插槽用于 UI 内容分发，不要和数据状态通信完全混为一谈。
标准答案
Vue 组件通信我一般按关系分类。 父传子最常用 props；子通知父用 emits。需要双向表单语义时可以用 v-model，在 Vue3 中本质还是 prop + update 事件约定。 如果父组件确实需要直接访问子组件暴露能力，可以使用 template ref，配合 defineExpose，但这种方式耦合更强，不应该替代正常的数据流。 跨多层组件可以用 provide / inject，适合主题、表单上下文、组件库内部上下文等。 多个无直接层级关系的组件共享业务状态，一般放到 Pinia/Vuex 这类 store。大型应用不建议用全局 EventBus 作为主要状态通信机制，因为依赖关系难追踪和维护。 另外 slot 主要解决父组件向子组件传递 UI 内容/渲染结构；作用域插槽允许子组件向插槽内容暴露数据。
答案整体解析
这题的关键不是列 API 越多越好，而是按父子、跨层级、全局状态分类，并说出各自的边界。
高频追问 + 答案
追问 1：为什么不推荐到处用 EventBus？
依赖是隐式的，事件来源/去向难追踪，生命周期清理和调试成本高。
追问 2：provide/inject 能不能做全局状态管理？
可以承载共享响应式值，但大型业务状态通常还是 Pinia 更有明确约束、DevTools 和模块组织。
追问 3：父组件调用子组件方法怎么做？
template ref 获取组件公开实例；script setup 子组件通常通过 defineExpose 明确暴露能力。
失分点 / 易错点
常见失分：零散列 props、$emit、Vuex，没有先按组件关系分类。
记忆钩子
父子 props/emits；跨层 provide/inject；共享状态 Pinia；直接实例 ref 慎用。
前置知识 / 关联知识
前置：单向数据流。关联：v-model、provide/inject、Pinia、slot。
#09
Vue Router 有哪些路由守卫？
S级 题型：API完整性 / 刁钻 刁钻度：★★★★★ 来源样本：水滴真题
训练目标：30 秒结论 + 90 秒展开 + 2～3 层追问
题目主要考察点和方向概述
1. 全局：beforeEach / beforeResolve / afterEach。
2. 路由独享：beforeEnter。
3. 组件内：beforeRouteEnter / beforeRouteUpdate / beforeRouteLeave；Composition API 有 update/leave 对应函数。
4. 继续追问执行顺序、next、this、鉴权和埋点场景。
标准答案
Vue Router 的守卫我按三类记。 第一类是全局：router.beforeEach、router.beforeResolve、router.afterEach。beforeEach 是全局前置守卫；beforeResolve 会在组件内守卫和异步路由组件解析完成后、导航确认前执行；afterEach 在导航完成后执行，因此不能再阻止导航，常用于埋点、标题等。 第二类是路由独享守卫 beforeEnter，写在具体 route record 上。 第三类是组件内守卫：beforeRouteEnter、beforeRouteUpdate、beforeRouteLeave。Composition API 中对应更新和离开还有 onBeforeRouteUpdate、onBeforeRouteLeave。 Vue Router 4 里推荐通过 return false / route location / Promise 等控制导航。旧的 next 参数目前仍兼容，但如果使用必须保证每条逻辑路径只调用一次。
答案整体解析
这就是水滴真实失分题。第一层回答必须做到“全局 / 独享 / 组件内”完整分类，不能只想到 beforeEach、afterEach。
高频追问 + 答案
追问 1：beforeResolve 和 beforeEach 区别？
beforeResolve 更靠后：在所有组件内守卫和异步路由组件解析成功后、最终导航确认前执行。
追问 2：afterEach 能取消导航吗？
不能。它是 after hook，没有能力影响已经结束的导航。
追问 3：beforeRouteEnter 为什么拿不到 this？
因为进入的组件实例当时还没有创建；旧式 next 回调可以在导航确认后拿到实例。
追问 4：完整执行顺序？
离开组件 beforeRouteLeave → 全局 beforeEach → 复用组件 beforeRouteUpdate → beforeEnter → 解析异步路由组件 → beforeRouteEnter → beforeResolve → 确认导航 → afterEach → DOM 更新。
失分点 / 易错点
你的真实失分：当时只答了 beforeEach 和 afterEach，没形成完整分类树。
记忆钩子
全局 → 独享 → 组件；beforeResolve 最后确认，afterEach 只能善后。
前置知识 / 关联知识
前置：Vue Router、组件生命周期。关联：鉴权、埋点、路由数据加载。
#10
Vue3 自定义指令有哪些生命周期？
S级 题型：API完整性 / 高刁钻 刁钻度：★★★★★ 来源样本：水滴真题
训练目标：30 秒结论 + 90 秒展开 + 2～3 层追问
题目主要考察点和方向概述
1. 7 个钩子：created；beforeMount/mounted；beforeUpdate/updated；beforeUnmount/unmounted。
2. 按“创建 1 + 挂载 2 + 更新 2 + 卸载 2”记。
3. 继续追问 Vue2→Vue3 映射、binding 参数、使用边界。
标准答案
Vue3 自定义指令有 7 个主要生命周期钩子。 created：元素 attribute 或事件监听应用前； beforeMount、mounted：挂载前和挂载完成后； beforeUpdate、updated：更新前和更新完成后； beforeUnmount、unmounted：卸载前和卸载完成后。 最好按“创建 1 + 挂载 2 + 更新 2 + 卸载 2”来记。 Vue3 还把命名尽量和组件生命周期对齐：Vue2 的 bind → beforeMount，inserted → mounted，componentUpdated → updated，unbind → unmounted；同时新增 created、beforeUpdate、beforeUnmount，Vue2 的 update 被移除。 自定义指令更适合复用底层 DOM 行为，例如自动聚焦、拖拽、点击外部、第三方 DOM 实例绑定等。如果逻辑本身是有状态业务逻辑，一般 composable 更合适；如果涉及 UI 结构复用，优先组件。
答案整体解析
这也是水滴真实失分题。它不深，但属于“高级前端应该熟悉的框架 API 面”。
高频追问 + 答案
追问 1：mounted 和 created 有什么区别？
created 时元素属性/事件监听甚至还没完全应用，mounted 时元素所在组件及相关节点已经完成挂载，更适合依赖真实 DOM 的操作。
追问 2：unmounted 一般做什么？
清事件监听、Observer、timer、第三方实例等手动副作用。
追问 3：指令钩子有哪些常用参数？
el、binding、vnode；更新相关还可拿 prevVnode。binding 中有 value、oldValue、arg、modifiers、instance 等信息。
追问 4：为什么多根组件上使用自定义指令要小心？
组件可能有多个根节点，指令无法自然确定应该落在哪个根元素上，Vue 会有相应限制/警告。
失分点 / 易错点
你的真实失分：平时只复习组件生命周期，突然切到“指令生命周期”时知识节点没建立。
记忆钩子
1 + 2 + 2 + 2 = 7。
前置知识 / 关联知识
前置：组件生命周期、DOM。关联：directive binding、composable、组件复用。
#11
Virtual DOM 是什么？Vue 的 Diff 核心思路是什么？
S级 题型：核心原理 刁钻度：★★★★☆ 来源样本：北京中小厂 / 滴滴
训练目标：30 秒结论 + 90 秒展开 + 2～3 层追问
题目主要考察点和方向概述
1. VDOM 是用 JS 对象描述 UI，不是为了“永远比 DOM 快”。
2. 更新流程：新旧 vnode 比较，再把必要变化 patch 到真实 DOM。
3. Vue3 编译器会给运行时静态信息，避免纯运行时全树遍历。
4. 列表 diff 重点理解 key，而不是死背源码分支。
标准答案
Virtual DOM 是用 JavaScript 对象描述目标 UI 的一种模式。组件 render 会产生 vnode 树，首次挂载时 renderer 根据 vnode 创建真实 DOM；状态变化后重新 render 得到新 vnode，再与旧 vnode 做 patch，只把必要变化应用到 DOM。 所以 VDOM 的核心价值不仅是性能，而是把声明式 UI 与平台 DOM 操作隔离，并提供可组合的渲染模型。 Vue3 和很多纯运行时 VDOM 的一个重要区别是：Vue 同时控制模板编译器和运行时，因此编译器可以提前识别静态节点和动态绑定，并给 vnode 加 PatchFlag、建立 Block 的动态子节点列表。更新时就可以跳过大量静态内容。 列表 diff 时 key 非常重要，它帮助判断节点身份和复用关系。不要把“Diff”简单背成某个算法名字，而应该先说明同层比较、节点身份、复用和最小 DOM 操作这些目标。
答案整体解析
这题适合把“VDOM、Diff、编译优化、key”串在一起。Vue3 的特点是 compiler-informed VDOM，而不只是运行时暴力 diff。
高频追问 + 答案
追问 1：Virtual DOM 一定比直接操作 DOM 快吗？
不一定。VDOM 有创建和 diff 成本，它的价值是声明式抽象、可维护性和跨平台等；针对特定极端场景的手写 DOM 可能更快。
追问 2：为什么通常只比较同层节点？
树结构 UI 更新可以借助节点类型和层级假设减少组合爆炸，跨层移动通常按删除+创建处理。
追问 3：Vue3 怎么减少全树 Diff？
缓存静态内容、PatchFlag 标记动态类型、Block/Tree Flattening 只追踪动态后代。
失分点 / 易错点
常见失分：回答“VDOM 比真实 DOM 快”，这是过度简化。
记忆钩子
render → vnode；update → new vnode → patch。Vue3：编译器告诉运行时哪里会变。
前置知识 / 关联知识
前置：render、DOM。关联：key、PatchFlag、Block Tree。
#12
v-for 为什么需要 key？为什么不推荐 index？
S级 题型：核心原理 刁钻度：★★★★☆ 来源样本：公开高频
训练目标：30 秒结论 + 90 秒展开 + 2～3 层追问
题目主要考察点和方向概述
1. key 表示 vnode 身份，帮助 diff 判断复用/移动/新建/删除。
2. 稳定唯一 key 能保留正确 DOM 与组件状态。
3. index 在插入、删除、排序时会变化，导致身份错配和状态复用问题。
标准答案
key 的作用是给同一层级的 vnode 提供稳定身份。列表更新时，Vue 需要判断某个新节点对应旧列表里的哪一个节点，从而决定复用、移动、创建还是删除。 如果使用稳定唯一的业务 id，节点身份不会因为列表插入、删除或排序而变化，Vue 可以更准确地复用 DOM 和组件实例。 index 不推荐作为 key，是因为 index 表示的是当前位置，不是业务实体身份。列表头部插入一个元素后，后面所有元素 index 都变了，如果子项里有输入框、本地组件状态等，就可能发生“旧状态复用到了另一个数据项”的问题。 但也不要绝对化：如果列表是完全静态、不排序、不插入删除，也没有需要保留的子项状态，index 的风险会小很多。
答案整体解析
这题不是“为了 Diff 更快”一句话结束。更核心的是 vnode identity 和状态复用正确性。
高频追问 + 答案
追问 1：key 是不是越随机越好？
相反。随机 key 每次 render 都变化，相当于告诉 Vue 所有节点都是新的，会导致反复销毁重建。
追问 2：什么时候 index 可以接受？
列表顺序永久稳定、只展示、没有局部状态时风险较低，但业务 id 仍更清晰。
追问 3：key 只影响 DOM 吗？
还会影响组件实例复用和本地状态生命周期。
失分点 / 易错点
常见失分：只说“不用 key 会影响性能”，没有回答身份和状态错配。
记忆钩子
key = 身份证；index = 座位号。
前置知识 / 关联知识
前置：VDOM、Diff。关联：组件复用、表单列表。

v-if 和 v-show 有什么区别？
S级 题型：核心API 刁钻度：★★★★☆ 来源样本：公开高频
训练目标：30 秒结论 + 90 秒展开 + 2～3 层追问
题目主要考察点和方向概述
1. v-if 是条件性创建/销毁；v-show 是始终渲染后切 display。
2. 初始开销 vs 高频切换开销。
3. v-if 是真正的条件渲染，分支内组件生命周期也会变化。
标准答案
v-if 和 v-show 都能控制显示，但机制不同。 v-if 是条件渲染：条件为 false 时，对应分支不会挂载；条件切换时可能创建或销毁组件、事件监听和 DOM，因此初始为 false 时成本较低，但频繁切换成本更高。 v-show 则通常会把元素正常渲染出来，再通过 CSS display 切换可见性，所以初始渲染有成本，但高频显示/隐藏更便宜。 因此低频切换、条件很少成立时更偏向 v-if；频繁切换，例如 Tab/面板显示隐藏，且节点本身不太重时可以考虑 v-show。
答案整体解析
回答不要停在“一个删除 DOM，一个 display:none”，还要给选型边界。
高频追问 + 答案
追问 1：v-if 里面组件的 mounted/unmounted 会不会重新执行？
分支真正销毁再创建时，会经历对应组件生命周期。
追问 2：v-show 能用在 template 上吗？
v-show 依赖真实元素的 display，因此和 v-if 的 template 条件分组能力不同。
追问 3：哪个性能一定更好？
没有绝对，取决于初始渲染和切换频率。
失分点 / 易错点
常见失分：没有把“切换频率”作为选型依据。
记忆钩子
v-if 真生灭；v-show 只显隐。
前置知识 / 关联知识
前置：组件生命周期。关联：keep-alive、条件渲染。
#14
Vue Router hash 和 history 模式有什么区别？
S级 题型：核心API 刁钻度：★★★★☆ 来源样本：滴滴
训练目标：30 秒结论 + 90 秒展开 + 2～3 层追问
题目主要考察点和方向概述
1. hash 使用 URL # 后部分，传统上不会作为路径发送给服务器。
2. history 使用 History API，URL 更自然，但服务器必须配置 SPA fallback。
3. 刷新 404 是 history 模式的经典工程追问。
标准答案
hash 和 history 的主要区别在 URL 形式和服务端配合。 hash 模式 URL 里有 #，例如 /#/user。# 后面的内容主要由浏览器前端路由处理，服务端拿到的请求路径通常不包含这部分，所以部署简单，刷新不容易因为前端路径导致服务端 404。 history 模式基于 History API，URL 可以是 /user 这种正常路径，可读性更好。但用户直接访问或刷新 /user 时，请求会真正到服务器，所以服务端必须配置 SPA fallback，把未知前端路由回退到 index.html，再交给前端 Router 匹配。 因此实际选择更多是产品 URL 需求、部署环境和服务端配置能力，而不是简单说 history 更高级。
答案整体解析
这是 Router 高频宽度题，重点是“刷新为什么 404”和服务器 fallback。
高频追问 + 答案
追问 1：history 刷新为什么 404？
因为浏览器直接向服务端请求 /user；如果服务端没有对应资源/路由，也没有回退 index.html，就返回 404。
追问 2：hash 改变会不会导致整页请求？
hash 变化通常用于客户端锚点/路由，不会像普通 path 导航那样发起整页资源请求。
追问 3：history 模式部署 Nginx 常怎么处理？
通常通过 try_files 等规则把不存在的前端路径 fallback 到 index.html。
失分点 / 易错点
常见失分：只回答“一个有 # 一个没有 #”。
记忆钩子
hash：# 前端自己玩；history：漂亮 URL，但服务器要兜底。
前置知识 / 关联知识
前置：URL、History API。关联：Nginx、SPA部署。
#15
Vue3 相比 Vue2 为什么更新效率更高？
S级 题型：编译优化 刁钻度：★★★★☆ 来源样本：公开高频
训练目标：30 秒结论 + 90 秒展开 + 2～3 层追问
题目主要考察点和方向概述
1. 不要答成“Proxy 所以 Diff 快”。响应式改造和渲染优化要分开。
2. 核心：模板编译器静态分析 → 缓存静态内容、PatchFlag、Block/Tree Flattening。
3. 运行时只做必要工作，而不是每次对整棵 VDOM 做同等强度比较。
标准答案
Vue3 更新效率更高，我会把原因分成“编译期优化”和“运行时改进”，而不是只回答 Proxy。 最核心的是 Vue3 的 compiler-informed VDOM。模板是可静态分析的，所以编译器可以提前判断哪些节点永远不变、哪些节点只有 class/text/props 某一类动态变化。 第一，静态内容会被缓存或提升，后续 render 可以复用，避免重复创建和 diff。 第二，动态 vnode 会带 PatchFlag。运行时通过位运算就知道这个节点到底需要更新 text、class 还是 props，不需要逐项盲比。 第三，Block / Tree Flattening 会把一个稳定结构中的动态后代收集到数组，组件更新时主要遍历这些动态节点，而不是完整遍历所有静态节点。 此外 Vue3 响应式改用 Proxy，能力更完整；调度、实现和运行时也有改进。但如果面试官问“编译为什么更快”，主线应该是静态缓存 + PatchFlag + Block Tree，而不是 Proxy。
答案整体解析
这是你之前已经重点补过的题。现在要形成稳定结构：响应式优化与渲染编译优化分层讲，避免混在一起。
高频追问 + 答案
追问 1：PatchFlag 是什么？
编译器在 vnode 上编码动态绑定的更新类型，运行时可以走针对性的 fast path。
追问 2：Block Tree 是什么？
Block 是内部结构相对稳定的模板区域，会记录带 PatchFlag 的动态后代；更新时遍历扁平化 dynamicChildren。
追问 3：v-if / v-for 为什么会形成新的 Block？
它们会改变结构，因此需要新的稳定边界来维护父 Block 的动态节点结构。
追问 4：Vue2 就完全没有静态优化吗？
不能把差异绝对化。Vue2 也有静态树优化，但 Vue3 的 compiler-informed VDOM、PatchFlag 和 Block/Tree Flattening 让编译器与运行时协同更深入。
失分点 / 易错点
常见失分：把“Vue3 编译优化”和“Proxy 响应式”混成一句，显得概念层次不清。
记忆钩子
Vue3 更新快：静态跳过 + 动态标记 + 动态树打平。Proxy 是另一条线。
前置知识 / 关联知识
前置：VDOM、Diff、模板编译。关联：PatchFlag、Static Cache、Block Tree。
