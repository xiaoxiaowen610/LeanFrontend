#01
type 和 interface 有什么区别？
S级 题型：核心类型 刁钻度：★★★★☆ 来源样本：编程猫社招 / 货拉拉
训练目标：30 秒结论 + 60～90 秒展开 + 常见追问
题目主要考察点和方向概述
1. 两者都能描述对象结构，很多场景可互换。
2. interface 更偏声明对象/类契约，支持 declaration merging 和 extends。
3. type 更通用：可表示联合、交叉、原始类型别名、tuple、条件类型等。
4. 不要机械背“interface 能扩展、type 不能”；type 可通过交叉类型组合。
标准答案
type 和 interface 都可以描述对象结构，很多业务场景里都能互换，但设计能力不同。 interface 更偏“对象结构契约”。它天然支持 extends，也支持 declaration merging，也就是同名 interface 可以合并。因此在公共库类型、可扩展对象模型、类实现契约等场景里很常见。 type 是更通用的类型别名机制。除了对象结构，它还能直接描述联合类型、交叉类型、元组、函数类型、条件类型、映射类型等。例如： type Status = 'idle' | 'loading' | 'done' type UserWithRole = User & { role: string } interface 也不是“不能做联合”，而是它自己不能直接声明成联合别名；type 在这类组合表达上更灵活。 我的使用习惯是：稳定对象契约、公共扩展点优先考虑 interface；复杂类型运算、联合/交叉/工具类型组合优先 type。
答案整体解析
这题最容易变成死背差异表。高级回答应该落到“表达能力”和“设计边界”上。
高频追问 + 答案
追问 1：interface 可以重复声明吗？
可以，同名 interface 会 declaration merging；type 同名重复声明会报错。
追问 2：type 能继承 interface 吗？
可以通过交叉类型组合，例如 type A = B & { x:number }。
追问 3：class implements 能不能实现 type？
只要 type 最终描述的是对象结构，可以 implements；但联合类型这类不适合作为 class 实现契约。
追问 4：团队里到底统一用哪个？
都可以，关键是建立一致约定。公共扩展型 API 常用 interface，复杂类型组合常用 type。
失分点 / 易错点
常见失分：说“interface 能继承，type 不能”，这是错误的简化。
记忆钩子
interface = 对象契约/可合并；type = 更通用类型表达式。
前置知识 / 关联知识
前置：对象类型、联合/交叉类型。关联：extends、implements、declaration merging。
#02
any 和 unknown 有什么区别？
S级 题型：核心类型 刁钻度：★★★★★ 来源样本：真实高频
训练目标：30 秒结论 + 60～90 秒展开 + 常见追问
题目主要考察点和方向概述
1. any 基本关闭类型检查，能读属性、调用、赋值给任意类型。
2. unknown 表示“现在不知道类型”，但使用前必须缩小类型。
3. any 会污染类型系统；unknown 更适合作为不可信输入的边界类型。
标准答案
any 和 unknown 都表示“类型暂时不确定”，但安全性完全不同。 any 相当于告诉 TypeScript：这个值你不要再检查了。它可以调用任意方法、访问任意属性，也可以直接赋值给其他类型，因此 any 很容易把不安全类型继续传播到整个调用链里。 unknown 则表示“我现在不知道它是什么，但在确认之前不能随便用”。unknown 可以接收任意值，但如果要访问属性、调用方法或赋值给更具体类型，就必须先通过 typeof、instanceof、自定义 type guard 等方式做类型收窄。 因此外部输入、不可信 JSON、catch error 等边界场景，unknown 通常比 any 更合理。 一句话：any 是放弃类型检查；unknown 是保留不确定性，但强迫你验证。
答案整体解析
高级前端要建立“边界输入先 unknown，再校验”的意识，这和后端返回数据运行时校验是同一套思维。
高频追问 + 答案
追问 1：unknown 能赋值给 string 吗？
不能直接赋，需要先缩小到 string。
追问 2：string 能赋值给 unknown 吗？
可以，任意类型都能赋给 unknown。
追问 3：any 能传染吗？
会。any 参与表达式、对象访问、函数返回后，往往让后续类型检查失去意义。
追问 4：catch 里的 error 为什么推荐 unknown？
因为运行时可以 throw 任意值，不一定是 Error；unknown 会强迫你先判断。
失分点 / 易错点
常见失分：只说 unknown 比 any 安全，却说不出“必须先 narrow”这一核心。
记忆钩子
any = 关掉检查；unknown = 先不知道，但用前必须证明。
前置知识 / 关联知识
前置：类型收窄。关联：API边界、zod、运行时校验。
#03
泛型是什么？为什么需要泛型？
S级 题型：核心类型 刁钻度：★★★★☆ 来源样本：字节 / 高级高频
训练目标：30 秒结论 + 60～90 秒展开 + 常见追问
题目主要考察点和方向概述
1. 泛型是在类型层给“类型”也加参数，让逻辑与具体类型解耦。
2. 核心价值：保留输入输出之间的类型关系，而不是用 any 丢掉信息。
3. 常见场景：函数、组件、API 响应、数据结构、工具类型。
4. 进一步追问：泛型约束 extends、默认泛型、keyof 联动。
标准答案
泛型可以理解为“类型参数”。函数参数让我们把运行时数据传进去；泛型让我们把类型也作为参数传进去。 比如： function identity<T>(value: T): T { return value } 如果传 string，返回值还是 string；传 User，返回值还是 User。这里最重要的不是“代码复用”四个字，而是泛型能保留输入和输出之间的类型关系。 如果用 any 写 identity(value:any):any，虽然也能接收所有类型，但返回值的具体类型信息丢了，后续代码失去提示和检查。 实际项目里泛型很常见，例如： ApiResponse<T> TableColumn<T> Promise<T> Map<K,V> React/Vue 组件 props 数据模型 请求函数 request<T>() 如果泛型不能是任意类型，可以通过 extends 做约束，例如： function getId<T extends { id: string }>(obj: T) { return obj.id } 所以泛型本质是：在保持类型信息的前提下复用逻辑。
答案整体解析
这题高级回答要把 any 对比带出来。泛型的核心不是“可以传任何类型”，而是“建立类型关系”。
高频追问 + 答案
追问 1：泛型和 any 最大区别？
any 丢掉具体类型关系；泛型把调用方实际类型保留下来并贯穿输入输出。
追问 2：extends 在泛型里一定是继承吗？
更准确是约束：T 必须满足某种类型条件。
追问 3：泛型可以有默认值吗？
可以，例如 type ApiResponse<T = unknown> = ...
追问 4：什么时候不该用泛型？
如果不同类型之间没有需要保持的关系，或者只有一个具体类型，强行泛型会增加复杂度。
失分点 / 易错点
常见失分：回答“泛型就是类型复用”，太空泛，没有说输入输出类型关系。
记忆钩子
泛型 = 给类型加参数；关键是“保留关系”，不是“随便什么都行”。
前置知识 / 关联知识
前置：函数类型、对象类型。关联：泛型约束、Utility Types、组件类型。
#04
常用 Utility Types：Partial / Required / Pick / Omit / Record / Readonly
S级 题型：API完整性 刁钻度：★★★★☆ 来源样本：货拉拉 / 高级高频
训练目标：30 秒结论 + 60～90 秒展开 + 常见追问
题目主要考察点和方向概述
1. Utility Types 本质是基于 mapped type / keyof 等能力组合出的常用类型转换。
2. Partial/Required/Readonly 改属性修饰；Pick/Omit 选字段；Record 构造键值映射。
3. 要会写业务场景，而不是只会翻译名字。
标准答案
这几个 Utility Types 我按用途记。 Partial<T>：把 T 的所有属性变成可选，适合编辑表单、PATCH 参数。 Required<T>：把所有属性变成必填。 Readonly<T>：把所有属性变成只读。 Pick<T, K>：从 T 里挑一部分字段。 Omit<T, K>：从 T 里排除一部分字段。 Record<K, V>：构造一个键集合 K 到值类型 V 的映射对象。 例如： type User = { id: string name: string age?: number } type UserPatch = Partial<User> type UserPreview = Pick<User, 'id' | 'name'> type UserForm = Omit<User, 'id'> type UserMap = Record<string, User> 从底层看，这些工具类型主要依赖 keyof、mapped types、条件类型等能力。因此面试如果继续追问，我至少要能说出 Partial 大致就是遍历 keyof T，把每个属性加上 ?。
答案整体解析
这类题属于“API 完整性 + 类型机制”。高级岗位不能只会名字，还要能说出 1~2 个真实场景。
高频追问 + 答案
追问 1：Partial 是深层 Partial 吗？
不是，内置 Partial 只作用于第一层属性。深层可选需要自定义递归类型。
追问 2：Readonly 是运行时真的不能改吗？
不是。它只在 TypeScript 编译期限制赋值，运行时对象仍是普通 JS 对象。
追问 3：Omit 底层怎么实现？
可以理解为 Pick<T, Exclude<keyof T, K>>。
追问 4：Record 常见场景？
枚举/联合 key 到配置对象、实体 id 到实体对象、状态码到文案等。
失分点 / 易错点
常见失分：能说定义，但没有业务例子，也不知道 Partial 不是递归的。
记忆钩子
Partial/Required/Readonly 改属性；Pick/Omit 选字段；Record 造字典。
前置知识 / 关联知识
前置：keyof、mapped types。关联：Exclude、Extract、DeepPartial。
#05
keyof、typeof、in 在类型系统里分别做什么？
S级 题型：类型操作 刁钻度：★★★★☆ 来源样本：字节
训练目标：30 秒结论 + 60～90 秒展开 + 常见追问
题目主要考察点和方向概述
1. keyof T：拿到类型 T 的属性键联合。
2. typeof value：在类型位置获取某个值的静态类型。
3. in：常用于 mapped type 中遍历 union key；运行时 in 也是类型收窄手段。
4. 三者常组合构造类型安全映射。
标准答案
keyof、typeof、in 是 TypeScript 里非常常用的类型操作符。 keyof T 会得到 T 的键组成的联合类型。例如： type User = { id:string; name:string } type UserKey = keyof User 结果就是 'id' | 'name'。 typeof 在类型位置里，可以获取某个已有变量或对象的静态类型： const config = { retry: 3, timeout: 1000 } type Config = typeof config 这样可以避免值和类型重复写两份。 in 在类型系统里经常用于 mapped type，遍历一个联合类型： type MyReadonly<T> = { readonly [K in keyof T]: T[K] } 另外运行时的 'name' in obj 也可以参与类型收窄。 这几个能力经常组合使用：typeof 从值拿类型，keyof 从类型拿 key，in 再遍历 key 构造新类型。
答案整体解析
这题的价值在于把 TS 从“写接口”提升到“做类型变换”。
高频追问 + 答案
追问 1：keyof any 大概是什么？
代表可作为对象属性键的类型集合，核心是 string | number | symbol。
追问 2：typeof 在 TS 和 JS 里一样吗？
语法名字相同但位置不同：JS typeof 是运行时运算符；TS 类型位置的 typeof 用来获取值的静态类型。
追问 3：in 只能做 mapped type 吗？
不是。运行时 `prop in obj` 也是 JS 运算符，TS 会利用它做类型收窄。
追问 4：为什么 typeof config as const 很常见？
as const 能保留更窄的字面量类型，再用 typeof/keyof 派生精确联合类型。
失分点 / 易错点
常见失分：把三个关键字混在一起，只会背语法但说不出组合关系。
记忆钩子
typeof：值→类型；keyof：类型→键；in：遍历键。
前置知识 / 关联知识
前置：联合类型。关联：mapped types、as const、类型收窄。
#06
TS 为什么不能保证后端运行时数据一定符合声明类型？
S级 题型：类型系统边界 刁钻度：★★★★☆ 来源样本：高级场景
训练目标：30 秒结论 + 60～90 秒展开 + 常见追问
题目主要考察点和方向概述
1. TypeScript 类型在编译后被擦除，运行时执行的仍是 JavaScript。
2. `as User`、接口声明、泛型 request<User>() 都不会自动验证网络响应。
3. 外部边界需要运行时校验：手写 guard、schema validator（如 Zod）、后端契约/生成代码。
4. 这是高级前端非常重要的“编译期 vs 运行时”边界意识。
标准答案
TypeScript 只能在编译期检查代码，不能自动保证后端真实返回的数据符合类型声明，因为 TS 类型在编译到 JavaScript 后基本会被擦除。 例如： const user = await request<User>('/api/user') 这里的 <User> 只是告诉 TypeScript“我期望它是 User”。如果服务端运行时真的返回： { id: 123, name: null } TypeScript 不会在浏览器里自动拦截它。 `as User` 更明显，它只是类型断言，不是类型转换，也不会做任何运行时检查。 所以外部边界数据如果可靠性要求高，需要额外做 runtime validation。常见方式有： 1. 手写 type guard； 2. 使用 Zod、Valibot 等 schema validator； 3. OpenAPI / JSON Schema 生成客户端，再配合运行时验证； 4. 后端契约测试与接口监控。 例如 Zod： const UserSchema = z.object({ id: z.string(), name: z.string() }) const user = UserSchema.parse(rawData) 这时才是真正对运行时数据做验证。 所以我的理解是：TypeScript 保证“代码内部类型关系”；Schema 校验保证“外部数据进入系统边界时是真的符合预期”。
答案整体解析
这是高级前端很能拉开差距的一题。很多人把 TS 当成运行时安全机制，真实项目里接口脏数据照样会把页面打崩。
高频追问 + 答案
追问 1：as User 会做数据转换吗？
不会。类型断言只影响编译器，不会修改运行时值。
追问 2：泛型 request<User>() 为什么也不安全？
泛型只改变调用方看到的静态返回类型，如果 request 内部没有 runtime validator，实际响应仍未经验证。
追问 3：是不是所有接口都必须 Zod parse？
不一定，要考虑性能、可信程度和业务风险。高风险边界、第三方数据、AI结构化输出、关键配置更值得严格校验。
追问 4：TS 和 Zod 为什么常一起用？
TS 管静态类型，Zod 做运行时 schema 校验；还可以通过 z.infer 从 schema 推导 TS 类型，减少重复定义。
失分点 / 易错点
常见失分：认为写了 interface 或 request<User>()，后端错误字段类型就会被 TS 自动拦截。
记忆钩子
TS 只管“编译时你怎么想”；Schema 才管“运行时数据到底是什么”。
前置知识 / 关联知识
前置：编译期/运行时。关联：Zod、API契约、AI Structured Output。
